# 2. 三条关键结论

## 结论 A：**STFT 反传可用（fp32）** —— 最大风险解除

原本 P4 里最担心的「STFT 反传不支持」**在 fp32 下完全正常**：

```
STFT 反传 ★训练必需 + 反传        8.43 ms   OK
完整 mel loss 链路 ★ + 反传       9.33 ms   OK
```

而且比 CPU 还快（CPU 对照 14.36 / 15.39 ms）。

⚠️ 但要注意日志里这行：

```
Aten Op fallback from XPU to CPU happends. This may have performance implications.
```

**说明 STFT 实际是在 CPU 上算的**，8.43 ms 已经包含了来回搬运的开销。可接受，但别以为是 GPU 在算。

## 结论 B：**bf16 在这台机器上没有收益，不用做**

这是最重要的发现。证据：

| 对比项 | fp32 | bf16 | 结论 |
|---|---|---|---|
| 矩阵乘 | 0.35 ms | 0.37 ms | 无收益 |
| Conv1d | 1.97 ms | 2.02 ms | 无收益 |
| **GAN mini step** | **6.88 ms** | **9.73 ms** | **bf16 慢 41%** |

再结合设备属性：

```
has_bfloat16_conversions = False
has_subgroup_matrix_multiply_accumulate = False
```

**torch 2.7.1 的 XPU 后端不认为 A750 有 XMX 单元**，所以 bf16 走的是模拟路径（或者根本没走矩阵引擎）。硬件上 Xe HPG 确实有 XMX，但这一版 torch + 驱动没有把它暴露出来。

**所以：不要用 bf16。全用 fp32。**

## 结论 C：**GRU 可用但慢，且只在 v2Pro 系列路径上**

```
GRU + 反传    187 ms   （fp32）
```

187 ms 是单项耗时最高的。查代码后确认：`nn.GRU` 只出现在 `module/models.py:682` 的 `ReferenceEncoder` 里（第 654 行的类），而 `ReferenceEncoder` **只被 v2Pro / v2ProPlus 使用**。

| 你要训的版本 | GRU 在路径上吗 |
|---|---|
| v3 / v4（走 `s2_train_v3_lora.py`） | ❌ 不在 |
| v2 / v2Pro / v2ProPlus | ✅ 在 |

**结论**：训 v4 的话 187 ms 不影响你；训 v2Pro 的话每 step 多 ~190 ms，能忍。

# 3. 对 P1 的修正

## 3.1 `is_half` 的推导方式要改

P1 里写的：

```python
is_half = eval(os.environ.get("is_half", "True")) and du.accel_available(device)
```

在这台机器上会得到 `True`，进而让推理用 fp16 —— 但 torch 报 `has_subgroup_matrix_multiply_accumulate=False`，fp16 大概率也没加速，还可能触发未测过的算子。

**改为**：

```python
is_half = eval(os.environ.get("is_half", "True")) and du.supports_fp16_fast(device)
```

`supports_fp16_fast()` 内部要求 `has_xmx and has_fp16`，这台机器返回 `False` → **推理走 fp32**。

⚠️ **顺序问题**：`inference_webui.py:89` 的 `is_half` 在 `device` 定义（L136-140）**之前**。两种改法：

```python
# 改法一：把 device 提前
device = str(du.default_device())          # 插到 L88 之前
is_half = eval(os.environ.get("is_half", "True")) and du.supports_fp16_fast(device)

# 改法二：不依赖变量
is_half = eval(os.environ.get("is_half", "True")) and du.supports_fp16_fast(du.default_device())
```

推荐改法二，改动最小。

## 3.2 `config.py` 会自然选 fp32，不用改

`get_device_dtype_sm()` 里：

```python
if dev_type == "xpu":
    if p["has_bf16"]:            # ← 本机 False
        return dev, torch.bfloat16, ...
    if du.supports_fp16_fast(dev):   # ← 本机 False
        return dev, torch.float16, ...
    return dev, torch.float32, ...   # ← 落到这里
```

**自动返回 fp32**，符合预期。P1 的 T1-2 不用额外改。

## 3.3 P1 的验收标准调整

| # | 原标准 | 新标准 |
|---|---|---|
| D5 | 日志显示 `dtype=bf16` | 日志显示 **`dtype=fp32`** |
| D4 | 推理出声 | 不变 |
| D2 | `bf16=True` | 改为 **`bf16=False`（预期，不是故障）** |

# 4. 对 P4 的修正

## 4.1 T4-6（STFT 兜底）→ **整节跳过**

原计划：如果 STFT 反传失败，做 CPU-side autograd 兜底。

实测：**fp32 下反传正常，不需要任何兜底**。

动作：
- 不创建 `module/mel_processing_xpu.py`
- 不改 `from module.mel_processing import ...` 这行
- 不需要 `probe_stft_xpu()`

**省下 2 天工期。**

## 4.2 T4-7（bf16 GAN 稳定性）→ **整节跳过**

不启用 bf16 就没有 GAN 发散问题。

动作：
- `_PRECISION` 自然落到 `"fp32"`
- 不做分层精度（`enc_q` / `flow` 不用单独拉回 fp32）
- 不用 `clip_grad_norm_` 替代 `clip_grad_value_`（可以保留原样）
- 不用 loss 有限性检查（可选保留，无害）

**再省下 1 天工期。**

## 4.3 P4 的 1a 代码**不用改**

因为：

```python
_PRECISION = "bf16" if (
    torch.device(device).type == "xpu" and du.supports_bf16(device)   # ← False
) else "fp32"
```

`du.supports_bf16()` 依赖 `has_bfloat16_conversions`，本机是 `False` → `_PRECISION = "fp32"`。

**代码自我修正，落到的就是我们要的分支。** 所有 `if _PRECISION == "bf16":` 的块都不会执行。

## 4.4 判据器 dtype 那节（T4-1j）

`net_d_dtype = next(net_d.parameters()).dtype` 在 fp32 下是 `torch.float32`，而 `y` 也是 fp32 → `.to(net_d_dtype)` 是空操作。

**建议保留这段代码**：它无害，而且如果以后 torch 更新支持了 bf16，改一个常量就能启用。

## 4.5 训练配置的数值

`fp16_run` 在 `s2.json` 里是 `true`，配合 `_PRECISION="fp32"` 时：

```python
scaler = amp.make_scaler(device, hps.train.fp16_run and _PRECISION != "bf16")
#                              True            and      True
#                          → make_scaler(device, True)
```

`make_scaler` 在 XPU 上**恒返回 `enabled=False` 的 scaler**，所以 `fp16_run=true` 不会真的开 fp16 缩放。

**建议直接改成 `false`**，语义更清楚：

```json
"fp16_run": false
```

# 5. 真实性能预期（修正之前的错误估算）

探针最后那行：

```
粗估：真实训练每 step ≈ 0.10s，5000 step ≈ 0.1 小时
```

**这个数字不可信**，它是拿 6.88 ms 的 toy GAN step × 10 外推的。真实模型参数量比那个 toy 大两个数量级，而且有判别器的多尺度卷积、KL loss、gradient 累积。

按同类模型的经验估算（**待你实测修正**）：

| 任务 | 3090 | A750 fp32（估） |
|---|---|---|
| s2 训练，1 分钟素材，bs=3，10 epoch | ~15 min | **1.5~3 h** |
| s1 训练，1 分钟素材，bs=4，10 epoch | ~1.5 h | **5~8 h** |
| 数据预处理（4 个脚本） | ~3 min | **5~8 min** |
| 推理 10 秒音频 | ~2 s | **6~10 s** |

**正确的测法**：跑起来后看日志里的 `[perf] step N: xxx ms/step`，跑满 100 step 拿中位数。
